# Where do Claude skills get published, and what does that demand of the repo?

Research for `topcv` (open-source Claude Code skill). Answers issue `04-distribution-channels.md`.

## TL;DR — the architecture-constraining findings

These are the answers the rest of the map is blocked on. Everything else in this doc is supporting detail.

1. **Bundling a binary is allowed, but it isn't the convention.** A Claude Code *plugin* can ship a `bin/` directory whose contents are added to the Bash tool's `PATH` while the plugin is enabled — this is an official, documented mechanism.[^plugins-ref] But Anthropic's own official plugins (the LSP language-server integrations) deliberately **don't** bundle their binaries — they require the user to install the binary separately (via brew/npm/system package manager) and just configure how Claude Code talks to it.[^discover-plugins] That's the load-bearing precedent for topcv's PDF renderer: **don't ship a compiled renderer binary in the repo.** Either (a) require a pre-installed renderer and degrade/guide-to-install if missing, or (b) install a renderer dependency on first run (see #2). A cross-platform compiled binary in `bin/` would also multiply the repo by every OS/arch you support, which cuts against every real skill repo's layout (all pure Markdown + scripts, no compiled artifacts — see Convention section).

2. **Downloading a dependency at runtime is explicitly sanctioned — but only because Claude Code has full network access.** Per Anthropic's own docs: "Claude Code: **Full network access** — Skills have the same network access as any other program on the user's computer... Global package installation discouraged: Skills should only install packages locally."[^overview] This is a *surface-specific* rule — the sandboxed Claude API/claude.ai Skills environment explicitly has **no network access and no runtime package installation**, so if any part of topcv's design doc gets written by someone thinking about the API sandbox, that assumption is wrong for Claude Code. There is also an official, documented pattern for exactly this: a plugin's `SessionStart` hook diffs a bundled manifest (e.g. `package.json`) against a copy cached in `${CLAUDE_PLUGIN_DATA}`, and runs `npm install` into that cache directory only when it changed — reused across sessions and plugin updates.[^plugins-ref] This is very likely the right shape for "get a PDF renderer onto this machine": install a JS/Python renderer package (e.g. via `npm install` or `pip install` into a cache dir) on first use rather than bundling or hand-rolling a downloader.

3. **There is an official, sanctioned place to persist per-user state outside the project — but it is not "$HOME at large."** Plugins get `${CLAUDE_PLUGIN_DATA}`, which resolves to `~/.claude/plugins/data/{plugin-id}/` — a directory that survives plugin updates, is shown to the user with its size before deletion, and is deleted automatically on uninstall (or kept with `--keep-data`).[^plugins-ref] This is the closest thing to a first-party "candidate profile" store. Two consequences for topcv:
   - **This mechanism is plugin-only.** A bare `.claude/skills/<name>/` (no `.claude-plugin/plugin.json`) does not get `${CLAUDE_PLUGIN_DATA}` or hooks with that variable — so if the profile needs a durable, tool-managed home, topcv should be packaged and distributed as a **plugin**, not a loose skill folder. This is a real fork in the road for the architecture ticket.
   - Writing to `$HOME` more broadly (outside `${CLAUDE_PLUGIN_DATA}`) is not itself forbidden by any distribution channel's policy — Claude Code's filesystem access is "the same access as any other program on the user's computer," gated only by the normal Bash/Write permission-prompt system, not a distribution-specific sandbox.[^overview] But using the ad-hoc path forfeits the free lifecycle management (survive updates, clean up on uninstall, visible size) that `${CLAUDE_PLUGIN_DATA}` gives for free.
   - Separately, a bundled skill's *own directory* is read-only/ephemeral at runtime in the plugin-cache sense — "the previous version's directory remains on disk for about two weeks after an update... but treat it as ephemeral and don't write state there,"[^plugins-ref] and "Installed plugins cannot reference files outside their directory" for *bundled* resources (no `../` traversal into other repo content once installed).[^plugins-ref] Neither of these blocks writing to `$HOME`/`${CLAUDE_PLUGIN_DATA}` at runtime via Bash — they only constrain what static files a plugin can *ship*.

4. **Executable scripts are not just allowed, they're the intended mechanism for deterministic work.** Anthropic's own architecture writeup is explicit: "Code: Executable scripts... that Claude runs using bash, providing deterministic operations without loading their code into context."[^skills-overview] This is exactly the shape a PDF-rendering step should take — a bundled script Claude shells out to, not inline generation. The `${CLAUDE_SKILL_DIR}` (bare skill) / `${CLAUDE_PLUGIN_ROOT}` (plugin) path variables exist specifically so a skill can pre-approve running its own bundled script without a permission prompt, via `allowed-tools: Bash(${CLAUDE_SKILL_DIR}/scripts/render.sh *)`.[^skills-doc]

5. **Size limits exist, but only on one channel, and they're generous.** Anthropic's own docs state no explicit repo/plugin size cap. The one hard number found is from `skills.sh`'s installer CLI (`npx skills add`, built by Vercel): **10 MiB per download, 25 MiB extracted, 1,000 files per archive**, by default — overridable via environment variable for trusted sources.[^vercel-skills] A rendering toolchain that pulls in a heavyweight dependency (e.g. a headless-Chromium PDF path) at install time would blow past this if bundled directly, which reinforces point 2 (install the dependency at runtime via npm/pip rather than vendoring it in the repo).

6. **There is no formal, published pre-merge review gate for "is this content safe" beyond automated screening — the community marketplace's exact rejection criteria for binaries/network calls/etc. are not publicly documented.** `claude plugin validate` checks manifest/frontmatter schema correctness only (structural, not content policy); submissions additionally go through unspecified "automated safety screening."[^plugins-guide] Nothing in the docs enumerates disallowed content. In practice, topcv doesn't need to pass this gate at all — see Channels, below: plain GitHub + a skills.sh listing is a complete, review-free distribution path that real widely-used skills (Matt Pocock's collection, `obra/superpowers`) actually use.

## 1–2. What channels exist in 2026, and how each one works

### `skills.sh` — real, not a false memory

**Verified.** `skills.sh` is a real site built and maintained by Vercel ("Made with care by Vercel").[^vercel-skills-fetch] It is a directory/search UI over an open-source CLI, `npx skills`, published as `vercel-labs/skills` on GitHub. It supports 75+ agent tools (Claude Code, Cursor, OpenCode, Cline, etc.), not just Claude Code — skills are meant to be tool-portable.

How it works:
- **Install:** `npx skills add <owner>/<repo>` pulls a skill (or a whole repo of skills) straight from GitHub — there is no separate "publish to skills.sh" step or per-package npm registry entry. Publishing *is* having a public GitHub repo with `SKILL.md` files in a discoverable layout; skills.sh indexes it.
- **Installation modes:** either **symlink** (recommended) or **copy**, at **project scope** (`./<agent>/skills/`) or **global scope** (`~/<agent>/skills/`).[^vercel-skills]
- **Constraints on what it will pull down:** 10 MiB/download, 25 MiB extracted, 1,000 files/archive by default (env-var override for trusted sources).[^vercel-skills]
- **No review/curation described** in the CLI's own docs — it's a mirror-and-index of GitHub content, not a submission queue. (Secondary-claim caveat: I could not find a published editorial/moderation policy for the skills.sh directory listing itself, only for the underlying install mechanics.)
- **Reproducibility:** it writes a project-root **`skills-lock.json`** — described by a secondary source (an explainer blog, not Anthropic or Vercel primary docs) as "the agent-skills equivalent of a package lockfile: it records which skills your repo expects, where they came from, and a hash snapshot the toolchain can use for updates."[^explainx] This matches this repo's own `skills-lock.json` exactly (see Local Evidence, below) — treat the *mechanics* as confirmed by direct inspection of this repo, and the *description* as a secondary characterization I couldn't independently verify against Vercel's own docs.

### Anthropic's official channels

**The `/plugin` command + plugin marketplaces** is Anthropic's actual first-party distribution mechanism, and it's richer than "just drop a SKILL.md":
- **`claude-plugins-official`** — Anthropic's own curated marketplace, auto-registered on first interactive launch. Inclusion is at Anthropic's sole discretion; there is no application process, and the community-submission form does **not** feed this marketplace.[^discover-plugins]
- **`claude-plugins-community`** (aka `claude-community`) — the public, third-party marketplace. Submission is via an in-app form (claude.ai admin settings, requires a Team/Enterprise org, or the Console form at `platform.claude.com/plugins/submit` for individual authors). Every submission runs `claude plugin validate` (schema/structure checks) plus unspecified automated safety screening. Approved plugins are pinned to a specific commit SHA in `anthropics/claude-plugins-community`'s `marketplace.json`, and CI auto-bumps the pin on new commits. Sync to the public catalog is nightly, so there's install lag after approval.[^plugins-guide]
- **Anyone can run their own marketplace** — a public/private git repo (GitHub, GitLab, self-hosted, or a local path) containing `.claude-plugin/marketplace.json`, added with `/plugin marketplace add owner/repo` (or a git URL, or a local path). This is a **complete, zero-gatekeeper distribution channel**: no Anthropic review, no size cap documented, just "does the file exist and is it valid JSON."[^marketplaces]
- Installing is `/plugin install <name>@<marketplace>`, with a choice of user/project/local scope.

**The `.claude/skills/` (project) and `~/.claude/skills/` (personal) convention** is the lowest-ceremony option — no manifest at all beyond `SKILL.md`'s own YAML frontmatter (`name`, `description`, required; several optional fields like `allowed-tools`, `disallowed-tools`, `paths`, `hooks`). This is "standalone configuration," explicitly positioned by Anthropic as the *starting point* before packaging as a shareable plugin — "Start with standalone configuration in `.claude/` for quick iteration, then convert to a plugin when you're ready to share."[^plugins-create] There's a documented one-command migration path (`plugin init` / copy `.claude/skills` into a plugin's `skills/`) for exactly this graduation.

**The Agent Skills open standard** (published by Anthropic at `agentskills.io`, released as a cross-platform standard 2025-12-18) is the format both `.claude/skills/` and skills.sh target: a folder with a mandatory `SKILL.md` (YAML frontmatter + Markdown body) and optional `scripts/`, `references/`, `assets/` subfolders. A skill built to this standard runs, largely unmodified, in Claude Code, Cursor, GitHub Copilot, Gemini CLI, and 20+ other tools.[^agentskills] This is worth designing topcv's SKILL.md against even though the ticket is Claude-Code-specific, since it's what skills.sh and most third-party collections assume.

**npm** is not, itself, a skill registry. It shows up only as the runner for the `npx skills` installer CLI (`skills.sh`'s tool). There is no "publish your skill as an npm package" convention found anywhere in the primary docs or the example repos inspected — GitHub is the actual artifact store in every real channel above.

**Plain GitHub + install instructions** — this is what most of the actually-popular skill collections use, with no marketplace at all: point users at `npx skills add owner/repo`, or `git clone` + copy into `.claude/skills/`, or `/plugin marketplace add owner/repo` if the repo happens to carry a `.claude-plugin/marketplace.json`. `mattpocock/skills` and `obra/superpowers` both work this way (see Convention section) — real, high-visibility distribution with zero formal review.

### Claude API / claude.ai sandbox (contrast only — not a distribution channel for Claude Code, but worth knowing the constraint doesn't apply here)

Skills used through the Claude API run in a sandboxed code-execution container: **no network access, no runtime package installation, pre-configured dependencies only**.[^overview] This is the opposite of Claude Code's "full network access, same as any program on the user's machine." Since topcv targets Claude Code specifically, the API's tighter sandbox is not a constraint on topcv's design — flagging only because it's easy to accidentally design against the wrong surface's rules.

## 3. Local evidence — what's actually installed on this machine, and what produced it

Inspected directly (not inferred):

- **`/Users/bonyadnouri/Projects/topcv/skills-lock.json`** — 21 skills, every one with `"source": "mattpocock/skills"`, `"sourceType": "github"`, a `skillPath` into that repo (e.g. `skills/engineering/tdd/SKILL.md`), and a `computedHash`. This is exactly the shape a `skills.sh`/`npx skills add mattpocock/skills` install produces, and matches the secondary description of `skills-lock.json` as a lockfile recording source + hash per skill for update-checking.
- **`.agents/skills/<name>/`** — the real files: `SKILL.md` plus, per skill, an `agents/` subfolder (bundled subagent definitions the skill's own instructions reference — matches the "subagent execution" frontmatter feature in Anthropic's skills docs) and occasional extra reference docs (`CONTEXT-FORMAT.md`, `GLOSSARY.md`, `mocking.md`, etc. — the `references/`-style bundled material the open standard describes, just flattened rather than nested in a `references/` subfolder).
- **`.claude/skills/<name>`** — every single entry is a **symlink** into `../../.agents/skills/<name>`. Nothing lives here independently.
- **`~/.claude/skills/`** (global) — a mix: some entries are real directories (one-off installs, e.g. `21st-ai`), most are symlinks into `~/.agents/skills/<name>` (mirroring the same pattern at the personal-scope level), and a few point at a completely different project's `.agents/skills/` via absolute path (leftover cross-project symlinks from prior work).

**What this means:** `.agents/skills/` is the tool-agnostic canonical storage location — "most agents now look for Skills under `.agents/skills/` instead of `.skills`," per the multi-agent-convention research.[^agents-convention] `.claude/skills/` is populated with **symlinks** purely so Claude Code's own discovery path finds the same files. This is consistent with, and directly explained by, skills.sh's own installer docs: "the Claude Code plugin installs the whole set as a managed, read-only bundle... or skills.sh copies [or symlinks] editable skill files into your project so you can modify them."[^explainx] The dual directories are not two competing distributions — they're one install (via `npx skills add`/skills.sh), with `.agents/skills/` as the source of truth and `.claude/` as a Claude-Code-specific access point. Confirms Anthropic's own docs too: "A `<skill-name>` entry in the enterprise, personal, or project locations can be a symlink to a directory elsewhere on disk. Claude Code follows the symlink."[^skills-doc]

Practical implication for topcv: **design the repo to be installable both ways** — as a plain skills-repo GitHub target for `npx skills add` (which will produce this `.agents/skills` + symlink pattern for adopters), and optionally as a `.claude-plugin/plugin.json`-bearing plugin for marketplace distribution. They are not mutually exclusive; `mattpocock/skills` ships both a plain skills tree *and* a `.claude-plugin/plugin.json` in the same repo (see Convention, below).

## 4. Convention — what well-regarded published skills actually look like

Three real repos inspected directly:

**`anthropics/skills`** (Anthropic's own examples, Apache-2.0-licensed for the open-source ones) — flat layout: `.claude-plugin/`, `skills/`, `spec/`, `template/`, `README.md`. Each skill self-contained in its own folder. The `skills/pdf` skill — directly relevant precedent for topcv's renderer — is: `SKILL.md`, `forms.md`, `reference.md`, `scripts/`, `LICENSE.txt`. No compiled binary anywhere in the tree; rendering logic lives in `scripts/` as source, invoked via bash at runtime.[^anthropics-pdf] This is the strongest single precedent available: Anthropic's own PDF-handling skill does *not* ship a renderer binary — it ships scripts and expects the runtime environment to provide the actual libraries.

**`mattpocock/skills`** ("Skills for Real Engineers," the collection this repo already has installed) — `.agents/`, `.claude-plugin/`, `.github/workflows/`, `.changeset/`, `docs/`, `scripts/`, `skills/engineering/*`, `skills/productivity/*`, plus root `package.json`/`package-lock.json` for its own tooling (not per-skill runtime deps). Ships **both** a plain skills tree (for `npx skills add`) and a `.claude-plugin/` (for marketplace install) from the same repo — confirming these two channels aren't exclusive. Per-repo state/config is handled by a dedicated setup skill (`setup-matt-pocock-skills`, present in this repo too) that writes small config docs under `docs/agents/*.md` in the *consumer's* repo rather than anywhere under `$HOME` — i.e., its "state" is project-scoped config, not user-scoped profile data, so it doesn't set precedent for topcv's candidate-profile problem directly.

**`obra/superpowers`** family — split across `obra/superpowers` (the plugin/framework), `obra/superpowers-skills` (community-editable skill content, MIT-licensed, fork+PR workflow), `obra/superpowers-marketplace` (the curated marketplace catalog), and `obra/superpowers-lab` (experimental skills). Repo-level split: `skills/` + `scripts/`. Per-user installed state lives at `~/.config/superpowers/skills/` — notably **not** under `~/.claude/` at all, showing that skill authors do sometimes pick their own `$HOME` subdirectory rather than relying on Claude-Code-specific mechanisms, though this predates (or simply doesn't use) `${CLAUDE_PLUGIN_DATA}`. (Note: `obra/superpowers-skills` itself is archived/read-only as of 2025-10-27, though the split repos above remain the live distribution.)

**Pattern across all three:** self-contained per-skill folders, `SKILL.md` + flat sibling reference `.md` files + a `scripts/` subfolder for anything executable, no compiled binaries checked in anywhere, and a `.claude-plugin/plugin.json` sitting alongside a plain skills tree rather than replacing it.

## 5. Naming — is `topcv` taken?

> **Outcome (2026-08-05): the name was changed to `candid-cv`** on the strength of the finding below. `candidcv` and `candid-cv` were both verified free on npm with no trademark or product collision. The rest of this section is the original research that drove the decision; references to `topcv` elsewhere in this document are the historical working title.

**Not taken as a skill/plugin name in the channels checked, but there's a real brand collision to flag.**

- **`anthropics/claude-plugins-community` marketplace** — fetched `marketplace.json` directly and scanned all ~2,332 `name` fields in the file: zero matches for `topcv`.[^marketplace-json] (Primary source, direct inspection — not a secondary claim.)
- **npm registry** — `GET https://registry.npmjs.org/topcv` returns `404 Not found`; registry search for `topcv` returns no results.[^npm] (Direct inspection.) Not that npm is a real skill channel (see above), but it's clean if anything ever needs a package name.
- **GitHub / skills.sh** — web search for `"topcv"` alongside `claude code skill`/`skills.sh` surfaces only generic CV/résumé-adjacent skills (`claude-ats-cv-skill`, `resume-builder-skill`, `resume-tailoring-skill`, etc.) — none named `topcv`.[^topcv-search] This is a search-based check, not an exhaustive index scan, so treat "nothing found" as reasonably strong but not airtight.

**The real collision is brand, not the skill ecosystem:** `topcv.com` is an established, actively-trading commercial CV/résumé-writing service (UK-founded, now broader), with its own trademark claims over "TopCV" per its own terms of service.[^topcv-brand] Naming an open-source Claude Code skill `topcv` invites confusion with that product even though no skill registry currently holds the name. Worth taking back to the user as an explicit naming decision before publishing — it's a five-minute rename now versus a takedown request later.
